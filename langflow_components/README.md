# Langflow-компоненты для структурного чанкинга НПА

Три кастомных компонента: загрузка документа в Qdrant и поиск по нему. Код
написан под тот же стек, что уже используется в проекте
(`lfx.custom.custom_component`, `langflow.schema.Data`, `qdrant_client`,
`fastembed`, Docling 2.148 из образа `langflow-custom`).

| Файл | Компонент | Роль |
|---|---|---|
| `eosz_structure_parser.py` | `EOSZ Structure Parser (B+C)` | PDF → структурные child/parent чанки |
| `qdrant_hybrid_ingest.py` | `Qdrant Hybrid Ingest (Dense + BM25 + progress)` | ваш ингест + отчёт о прогрессе |
| `qdrant_doc_admin.py` | `Qdrant Doc Admin (versions)` | payload-индексы, список редакций, удаление старых версий |
| `eosz_retriever.py` | `EOSZ Hybrid Retriever (Dense + BM25 + refs)` | поиск: точный lookup по номеру, expand-to-parent, 1-hop по ссылкам |

---

## 0. Прогресс в enterprise_ai_shop

Langflow не отдаёт прогресс выполнения через job API: снаружи видно только
`queued → running → completed`. Поэтому компоненты сами шлют прогресс по HTTP.

```
Langflow (парсер/ингест) ──POST──► /api/jobs/{id}/progress ──► ProcessingJob
                                       ▲                        │
                                       │                        ▼
                          X-Progress-Token              админка: полоска
```

### Что делает приложение

| Где | Что |
|---|---|
| `models.ProcessingJob` | поля `progress_stage/done/total/message/updated_at` |
| `app.MIGRATIONS` | `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (применится при старте) |
| `routers/jobs.report_progress` | `POST /api/jobs/{id}/progress`, токен в `X-Progress-Token`, отвечает 204 |
| `routers/jobs._progress_of` | отдаёт `progress` в `GET /api/jobs/{id}` и `GET /api/jobs` |
| `langflow_client.build_progress_tweaks` | прокидывает `job_id`/`progress_url`/`progress_token` в компоненты через tweaks |
| `routers/jobs.upload_and_run` | создаёт задачу **до** запуска flow (иначе `job_id` некуда деть) |
| `templates/admin_ingestion.html` | колонка «Прогресс»: полоска, стадия, «нет обновлений N мин» |
| `app.auth_middleware` | путь `/api/jobs/*/progress` вне сессионной авторизации |

### Стадии

`parsing` → `chunking` → `embedding` → `upserting` → `done`

Парсер берёт `parsing`/`chunking` из `progress_callback` Docling
(событие `PageCompletedProgress` содержит `completed_pages` и `total_pages`),
ингест — `embedding`/`upserting` по батчам.

### ETA («осталось ~N мин»)

Компоненты считают остаток сами: `(total - done) / (done / elapsed)`, то есть
по средней скорости с начала стадии. Средняя, а не мгновенная, потому что
Docling то разгоняется на текстовых страницах, то тормозит на таблицах.

В приложении хранится `progress_eta_seconds`, а наружу отдаётся ещё и
`eta_at` — абсолютное время окончания:

```json
"progress": {
  "stage": "parsing", "done": 70, "total": 100, "percent": 70,
  "eta_seconds": 16, "eta_at": "2026-11-23T12:50:01.512780"
}
```

В админке это выглядит как `осталось ~16 мин (≈ 14:32)`. Время окончания
берётся с сервера: страница обновляется раз в 10 секунд, и «осталось N
секунд» успевало бы устареть, а время окончания остаётся верным.

Оценка не появляется сразу: первые 3 секунды стадии и `done = 0` дают
`eta_seconds: null` — считать ещё не по чему.

### Настройки

```env
PROGRESS_TOKEN=<общий секрет; пусто — берётся SECRET_KEY>
PROGRESS_BASE_URL=http://host.docker.internal:5001
```

`localhost` внутри контейнера Langflow указывает на сам Langflow, поэтому
адрес приложения — `host.docker.internal`.

**Обязательное условие:** у сервиса `langflow` в compose должна быть строка

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```

Без неё имя не резолвится, и прогресс молча не доходит (в логе Langflow
будет `Прогресс не отправлен ...`). Проверка:

```bash
docker exec langflow getent hosts host.docker.internal     # должен вернуть IP
docker exec langflow curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST http://host.docker.internal:5001/api/jobs/probe/progress \
  -H "X-Progress-Token: <токен>" -d '{}'
# 404 = эндпоинт найден (job не существует) — всё настроено верно
# 401 = неверный токен ИЛИ запрос попал на старую версию приложения
```

**Альтернатива при переносе в одну docker-сеть.** Вместо хоста можно
указать имя сервиса:

```env
PROGRESS_BASE_URL=http://enterprise-ai-shop:5001
```

Условия, при которых это заработает:

1. приложение и langflow — в одной сети (`langflow-network`);
2. порт — тот, что слушает uvicorn **внутри** сети;
3. образ приложения пересобран: в старом нет `/api/jobs/{id}/progress`.

Замер на этой машине:

```
host.docker.internal:5001  -> 404   ✅ рабочий вариант
enterprise-ai-shop:5001    -> 401   ❌ имя резолвится, но в контейнере
                                       старый образ без эндпоинта
```

Если `enterprise-ai-shop` отвечает на `/health` редиректом `302` на
`/auth/login` — это верный признак, что там старая версия кода.

Если `PROGRESS_TOKEN` пуст и `SECRET_KEY` дефолтный — прогресс работать
будет, но токен станет предсказуемым. Задайте явно.

### Троттлинг

Docling зовёт колбэк на каждую страницу: 673 страницы — 673 HTTP-запроса.
Компоненты отправляют не чаще раза в `progress_interval` секунд (3 — парсер,
2 — ингест) плюс всегда финальную стадию. Ошибка отправки не роняет разбор:
`try/except` и строка в лог.

## 1. Как подключить

Langflow → **Settings → Custom Components → Create New**, вставить содержимое
файла, сохранить. Имя класса менять нельзя: Langflow привязывает компонент к
классу, а не к имени файла.

Компоненты требуют пакетов, которые уже стоят в `Dockerfile.custom-langflow`
(`docling`, `tiktoken`, `fastembed`) и в базовом образе (`qdrant_client`,
`pandas`). Ничего доустанавливать не нужно.

## 2. Схема flow

### Загрузка (один раз на редакцию)

```
Read File ──► EOSZ Structure Parser (B+C) ──► Qdrant Hybrid Ingest ──► Chat Output
                        ▲
                        └── page_from / page_to (пакет по 40–60 страниц)
```

`Qdrant Hybrid Ingest` менять не нужно: парсер отдаёт `list[Data]` с полем
`text` и плоским `data`, а ингест копирует весь `data` в payload.

Порядок для документа на 673 страницы:

1. `Qdrant Doc Admin` → `action=collection_info` — убедиться, что коллекция есть.
2. Прогнать пакеты: `page_from=1..60`, `61..120`, … Причина не в лимите
   Docling, а в `LANGFLOW_WORKER_TIMEOUT=600`: парсинг идёт ~2–4 с/страницу,
   60 страниц — это 2–4 минуты плюс эмбеддинг.
3. `Qdrant Doc Admin` → `action=ensure_indexes` (один раз на коллекцию).
4. `Qdrant Doc Admin` → `action=list_documents` — проверить, что редакция
   одна и число точек совпадает с ожидаемым.

### Обновление редакции

1. Прогнать новый PDF через парсер с новым `doc_version`
   (пусто = определяется автоматически по дате последнего изменения на титуле).
2. `Qdrant Doc Admin` → `action=delete_old_versions`, `doc_id=<id>`,
   `keep_version=<новая>`, сначала с `dry_run=true`.
3. Выключить `dry_run` и повторить.

Версия входит в `chunk_index` (`2020-07-17:1234`), а `Qdrant Hybrid Ingest`
считает point id как `uuid5(filename::chunk_index::text)`. Поэтому:

* повторный ингест той же редакции перезаписывает те же точки (идемпотентно);
* новая редакция получает новые id и не конфликтует со старой;
* удаление старой редакции — точечное, по фильтру, без пересоздания
  коллекции (в одной коллекции могут лежать другие документы).

`text` каждого чанка начинается с breadcrumbs:

```

Перечень продукции, в случае осуществления закупок которой проводится аукцион (1) / редукцион (2)

…

Условия применения (сноски):
— (1) Закупка продукции… если плановая стоимость закупки (лота) не превышает
  10 миллионов рублей с НДС…
```

Это то, что эмбеддится: модель видит и иерархию, и номер пункта, и условие
применения, а не только абзац.

## 3.1. Поиск: `EOSZ Hybrid Retriever`

### Схема

```
Chat Input ──► EOSZ Hybrid Retriever ──┬──► Prompt (context) ──► LLM ──► Chat Output
                     ▲                 └──► Retrieved Chunks (documents)
                     │
        EmbeddingModelComponent (Qwen3-Embedding-0.6B)
```

Два выхода: `documents` — список `Data` с цитатами для отладки и UI,
`context` — готовый пронумерованный блок `[1] … [2] …` для промпта.

### Порядок работы

1. **Определение редакции.** Если `doc_version` пусто, ретривер сканирует
   коллекцию и берёт самую позднюю редакцию для указанного `doc_id`. Иначе
   при двух редакциях в выдачу попадали бы и старый, и новый пункт с одним
   номером.
2. **Разбор запроса.** Из вопроса достаются номера: `п. 4.2.2`, `пункт 4.2.2`,
   `статья 7.12`, `приложение 9`, `глава 7`.
3. **Точный lookup.** По `clause_key` / `article_no` / `appendix_no` /
   `chapter_no`. Для «п. 2.1» внутри Приложения 12 пробуются оба варианта:
   `clause:2.1` и `clause:12.2.1`.
4. **Гибридный поиск.** dense + BM25, слияние через RRF на стороне Qdrant,
   фильтры `chunk_type=child`, `doc_id`, `doc_version`.
5. **1-hop по ссылкам.** У найденных чанков читается `ref_keys`; при
   `ref_scope=appendix` ссылка вида `clause:` сначала разрешается внутри
   приложения («п. 2.1» → `clause:12.2.1`), и только если там пусто — по
   всему документу. Ссылки на статьи, приложения и главы ищутся в своих
   полях (`article_no`, `appendix_no`, `chapter_no`), а не в `clause_key`.
   Максимум `max_ref_hops` штук, каждая помечается `source="ref"` и `via_ref`.
6. **expand-to-parent.** Первые `expand_parents` результатов заменяются
   parent-чанком (статьёй целиком), потому что условие или исключение часто
   остаётся абзацем выше найденного пункта.
7. **Цитата.** В начало текста добавляется
   `ЕОСЗ (ред. 2020-07-17), Приложение 12, п. 2.1, стр. 366`.

### Настройки

| Параметр | Значение | Зачем |
|---|---|---|
| `top_k` | 8 | сколько фрагментов уходит в промпт |
| `prefetch_limit` | 30 | кандидатов на каждый из двух поисков до RRF |
| `expand_parents` | 4 | сколько заменить полным parent-чанком |
| `use_exact_lookup` | true | точный поиск по номеру пункта |
| `use_ref_expansion` | true | 1-hop по перекрёстным ссылкам |
| `ref_scope` | `appendix` | где разрешать ссылку: в приложении или по документу |
| `max_ref_hops` | 3 | ограничение на добавку по ссылкам |
| `min_score` | 0.0 | порог RRF; подбирать по eval, не «на глаз» |
| `include_citation` | true | цитата в начале текста |

### Что в `data` каждого результата

`score`, `source` (`exact` / `hybrid` / `ref`), `via_ref`,
`expanded_to_parent`, `citation`, `clause_number`, `clause_key`,
`article_no`, `appendix_no`, `section_path`, `page_from`, `page_to`,
`block_type`, `table_caption`, `doc_id`, `doc_version`, `ref_keys`.

`source` удобно выводить в UI: `exact` — сработал номер пункта, `ref` —
фрагмент подтянут по ссылке (модель должна знать, что это контекст, а не
прямой ответ), `hybrid` — обычный семантический поиск.

## 4. Решения, которые важны для качества

**Номера пунктов берутся из `item.orig`, а не `item.text`.** Docling выбрасывает
нумерацию из `text` («1.1. не применяются…» → «не применяются…»). Без `orig`
цитата «п. 2.1» невозможна.

**Иерархия — по `section_header`.** `ГЛАВА N`, `Статья N.M`, `Приложение № N`,
`Раздел N`, остальные заголовки — подраздел. Колонтитулы приложений
(«Приложение 9 к Единому отраслевому стандарту…») повторяются на каждой
странице, распознаются отдельно и не попадают в текст.

**Слияния ячеек раскрываются по `row_span`/`col_span`.** В Приложении 9 одна
ячейка «Оборудование компьютерное…» занимает 12 строк; без раскрытия коды
ОКПД2 остаются без наименования продукции. Дополнительно «№ | Наименование»
переносится с предыдущей страницы, когда таблица продолжается.

**Сноски приклеиваются к таблице и повторяются в каждом её чанке.** Условие
«запрос котировок, если НМЦ ≤ 10 млн руб.» живёт в сноске под таблицей.
Если её оторвать, ответ про способ закупки будет неверным.

**Вводная фраза пункта повторяется при дроблении.** Подпункты «а)–е)» без
«Стандарт не применяется заказчиками…» теряют смысл.

**Оглавление и номера страниц не индексируются.** `document_index`,
`page_header`, `page_footer` и строки вида `237` отбрасываются.

**parent-чанк не дублирует одиночный child.** Если parent состоял бы из одного
child, он не создаётся: экономия точек без потери контекста.

## 5. Настройки по умолчанию и почему такие

| Параметр | Значение | Обоснование |
|---|---|---|
| `max_child_tokens` | 350 | пункт целиком, но без склейки соседних статей |
| `max_parent_tokens` | 1800 | статья или группа пунктов целиком для LLM |
| `max_parent_chars` | 2000 | потолок под `max_model_len` модели эмбеддингов |
| `attach_footnotes` | true | в сносках условия применения норм |
| `emit_parents` | true | expand-to-parent в ретривере |
| `extract_refs` | true | основа 1-hop по ссылкам |
| `emit_tables_as_rows` | true | иначе таблица режется как текст и теряет шапку |

### Почему появился `max_parent_chars`

У `Qwen3-Embedding-0.6B` в этом деплое `max_model_len=1024` токена, а
русский юридический текст упирается в этот лимит на ~2400–2800 символах
(проверено: 2400 проходит, 2800 — 400 Bad Request). Parent-чанк не ищется
вектором, но `Qdrant Hybrid Ingest` эмбеддит всё, что получил, поэтому
parent на 4300 символов ронял ингест целиком.

Отсюда два ограничения в парсере:

* накопление parent останавливается на `max_parent_chars`;
* если parent всё равно длиннее (один крупный child), он режется по абзацам,
  а сегменты получают `parent_part` и разные `parent_id` (первый сохраняет
  исходный id, на него ссылаются child-чанки).

Если поднимете `--max-model-len` у vLLM до 4096, `max_parent_chars` можно
увеличить — статья будет попадать в LLM целиком.

### Почему `skipped` бывает больше нуля

`skipped` в итоге ингеста — это НЕ норма. Каждый пропуск означает фрагмент,
которого не будет в поиске. Разбивка причин печатается в ответе компонента:

```json
{"upserted": 4553, "skipped": 0, "total": 5257,
 "skipped_breakdown": {"truncated": 704},
 "embed_error": null}
```

| Причина | Что значит | Что делать |
|---|---|---|
| `empty` | чанк пришёл с пустым текстом | смотреть парсер/промежуточные компоненты |
| `embed_failed` | модель не осилила текст даже частями | поднять `--max-model-len` у vLLM |
| `sparse_failed` | сбой BM25-энкодера | обычно падение памяти/модели |
| `upsert_failed` | Qdrant отверг точку | смотреть лог с текстом ошибки |
| `truncated` | текст урезан для эмбеддинга | НЕ потеря: в payload полный текст |

**Важно про `truncated`:** режется только то, что уходит в модель
эмбеддингов. В `payload["text"]` остаётся полный текст, поэтому LLM получает
его целиком — страдает лишь точность вектора на очень длинных чанках.

### Почему нельзя терять батч целиком

Раньше ошибка эмбеддинга обнуляла весь батч: один parent длиннее лимита
ронял запрос на 64 текста, и 63 исправных чанка не попадали в Qdrant.
В логах это выглядело как «пропущено 704» без объяснений — ровно 11 батчей
по 64.

Теперь ингест деградирует: батч → по одному → усечение вдвое (1800 → 900 →
450 → 200 символов). Проверено на тексте из 7200 символов: **3 из 3 чанков
записаны, потерь нет**.

## 6. Ограничения

* **Таймаут воркера.** 673 страницы не проходят в один job — используйте
  `page_from`/`page_to`.
* **ДВА разных таймаута Langflow.** Это самая частая причина «процесс шёл,
  а в Qdrant пусто»:

  | Переменная | По умолчанию | Что ограничивает |
  |---|---|---|
  | `LANGFLOW_WORKFLOW_EXECUTION_TIMEOUT` | **300 с** | потолок времени одного запуска; именно она даёт `exceeded 300s execution ceiling` |
  | `LANGFLOW_WORKER_TIMEOUT` | 300 с | время жизни задачи в очереди воркера |

  Обе надо поднять (в проекте — 3600). Проверить фактическое значение:

  ```bash
  docker exec langflow sh -c 'echo $LANGFLOW_WORKFLOW_EXECUTION_TIMEOUT'
  docker exec langflow /app/.venv/bin/python -c \
    "from langflow.services.deps import get_settings_service; \
     print(get_settings_service().settings.workflow_execution_timeout)"
  ```

  Настройка живёт в `lfx/services/settings/groups/runtime.py`, читается с
  префиксом `LANGFLOW_`. Если переменная не задана — потолок 300 с, и
  документ на 673 страницы будет убит примерно на середине разбора: парсер
  не дойдёт до ингеста, в Qdrant ничего не запишется.
* **Скорость.** Замерено на этом документе: ~1 с/страницу после прогрева
  моделей (26 страниц за 25 с). На 673 страницах это 12–25 минут парсинга
  плюс эмбеддинг.
* **Версия при пакетном прогоне.** Если пакет не включает титульный лист,
  дата редакции не определяется и подставляется `doc_hash`. Для пакетов
  задавайте `doc_version` явно: хеш считается по всему файлу и одинаков для
  всех пакетов, но это не дата, и в payload попадёт нечитаемая строка.
* **Ссылки.** Извлекаются регулярками, точность ~85–92 %; «п. 2.1» внутри
  приложения и «п. 2.1» Стандарта различаются только по области видимости —
  это решается в ретривере, а не здесь.
* **BM25 по русскому** (`Qdrant/bm25`) работает без стемминга: падежи
  («закупок» / «закупки») может не поймать, гибрид с dense это компенсирует.
* **Создание payload-индексов медленное.** REST-вызов блокируется до
  окончания постройки: на 12 индексах уходит до пары минут. Это разовая
  операция, `timeout` в компоненте — 120 с.
* **`scroll` в Qdrant на диске медленный.** На этой машине `scroll` по
  коллекции занимал 50–95 с и иногда отдавал 500, тогда как `query_points`
  и `facet` — 0.002 с. Поэтому ретривер и `Qdrant Doc Admin` не используют
  `scroll`: точные попадания ищутся через `query_points` с жёстким фильтром
  (HNSW читает из памяти), а список редакций — через `facet`. Если увидите
  `scroll` в чужом компоненте — это причина «подвисаний на ровном месте».
* **Первый запрос после старта воркера — 30–60 с** (загрузка BM25 + прогрев
  vLLM). Дальше 0.1–0.5 с. При `LANGFLOW_WORKERS=3` каждый воркер
  прогревается отдельно.
* **`facet` без фильтра.** В этой версии `qdrant_client` `facet(filter=...)`
  не поддерживается — код ловит `TypeError` и работает без фильтра, поэтому
  версия выбирается по всем документам коллекции. Если в одной коллекции
  лежат разные документы с разными версиями, задавайте `doc_version` явно.
* **Титул и оглавление** (стр. 1–4) дают 1–2 чанка без иерархии: в пакетном
  прогоне они попадают в первый пакет, и это нормально.

### Правило отсечения слабых ref

Ссылочные хиты не должны вытеснять сильные hybrid-попадания. Проверка на
реальном запросе показала: при жёстком приоритете `ref` фрагмент Приложения 12
(score 0.41) вытеснял Приложение 9 (score 0.83) — то есть прямой ответ на
вопрос уезжал на второе место. Поэтому:

* `exact` — всегда первым (пользователь явно спросил номер);
* `ref` и `hybrid` — по score;
* `ref` отбрасывается, если его score меньше половины лучшего `hybrid`.

Порог 0.5 — эмпирический, его стоит подобрать по eval-набору.
